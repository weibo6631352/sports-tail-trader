# 系统工作流

## 0. 心智模型

整个 polymarket_trader 后端 = **1 个 `TradingWorkflow` 实例 + 围绕它的 runtime 基础设施**。
没有"策略"层、没有"策略选择"——就是一个量化交易工作流。

### 工作流定义

系统有两个工作流：

- **主工作流**：1 条端到端管道，由外部数据持续驱动
  - 数据入口（discovery + WS + 直播 + 赔率）→ 决策响应 → 执行 → 反馈
  - 持续运行，事件驱动；无新事件就不跑决策
- **兜底工作流**：周期性恢复路径
  - 20s 一次 reconcile，清主路径碰不到的边缘状态（僵尸单 / 漏挂 SELL / 全局降级）

代码层面这两个工作流共享一个 `QuantDecider`，靠 `QuantTriggerKind` 分派分支：

```python
class QuantTriggerKind(StrEnum):
    MARKET_TICK = "market_tick"          # 主工作流的"决策响应层"入口
    RECONCILE_CYCLE = "reconcile_cycle"  # 兜底工作流入口
```

### 决策响应层内嵌的入场门禁

入场门禁**全部在 QuantDecider 内部**完成，不是独立链路：

1. universe 门禁 — `TradingWorkflow.select_market` 在**数据入口层 ①** 就已过滤
2. market family 路由 — SINGLE_GAME / OUTRIGHT / SERIES / ESPORTS 分派
3. Kelly sizing — 价格上限 / 流动性 / min edge / per-market cap / drawdown halt
4. capital efficiency gate — 预期毛利 / 资金占用时长
5. 现金硬下限 — context.available_usdc < $5 直接 skip

通过所有门禁 → 产出 BUY `TradingDecision`。

## 2. 兜底工作流（reconcile，周期性）

```
periodic_reconcile scheduler job (20s)
    ↓
ReconcileWorker → ReconcileService.build_market_plan
    ↓ 构造 DecisionContext(trigger=reconcile_cycle)
TradingWorkflow.quant_decide
    ↓
QuantDecider._decide_reconcile (recovery 子流程)
    ↓ recovery actions
ReconcileActionApplier → OrderExecutor
```

职责：
- 清僵尸订单（chain 上还在但 store 没记的 open order）
- 补漏挂的 SELL（高成本仓位漏挂 profit-take）
- 全局降级 pause（直播源全断时主动暂停 single_game 入场）
- 与主工作流共享同一个 `QuantDecider` 实例，但走 `reconcile_cycle` 分支

**为什么需要兜底**：主工作流是事件驱动的，盘口长期不推送 / WS 断线 / 重启后状态丢失等场景下，主路径不会自发响应——靠 reconcile 周期扫描兜住。

## 3. 状态真相源（CLAUDE.md §3 不可违反）

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | Polymarket 实时事件 + 权威快照 | 决策真相 |
| 2 | 内存 stores（AccountState / MarketRegistry / MarketMetadata / Orderbook*） | P0 热路径读取 |
| 3 | PostgreSQL | **仅审计**，不参与运行时决策 |

DB 异步落库走 outbox → PersistenceWorker，**绝不反向阻塞决策路径**。

## 4. Runtime 装配（main.py `build_runtime`）

```
基础设施
  ├─ Polymarket clients (Gamma / Clob / Data / WS)
  ├─ Goalserve clients (inplay / livescore / pregame / lazy)
  ├─ ThreadPools (trading / maintenance / process)
  └─ Settings + LoggingRuntime + MetricsRegistry

内存 stores
  ├─ MarketRegistry / GammaMarketSnapshotStore
  ├─ AccountStateStore / MarketMetadataStore
  ├─ OrderbookDeltaStore / OrderbookHistoryBuffer / OrderbookDerivedStore
  └─ SeasonStateStore

TradingWorkflow
  └─ TradingWorkflow(config=TradingWorkflowConfig, ports=RuntimePorts)
      └─ 内部装配 QuantDecider

Services
  ├─ MarketIngestService            (数据入口层 ①)
  ├─ DecisionContextBuilder         (决策响应层)
  ├─ ReconcileService               (兜底工作流)
  └─ OrderGateway + RiskManager + OrderExecutor  (执行层)

Workers
  ├─ 数据入口层
  │   ├─ MarketDiscoveryWorker  (P2)
  │   ├─ MarketWsWorker         (P0)
  │   ├─ SportsLiveStateWorker  (P2)
  │   └─ Season/Game/Pregame OddsWorker (P2)
  ├─ 决策响应层
  │   └─ MarketTickWorker       (P0)
  ├─ 反馈层
  │   └─ UserWsWorker           (P0)
  ├─ 兜底工作流
  │   └─ ReconcileWorker        (P2)
  └─ 旁路审计
      └─ PersistenceWorker       (P3, audit only)

Paper 模式（settings.paper_trading_mode=true 时）
  └─ build_paper_runtime → PaperVirtualLedger + 4 个 background task

Scheduler + Supervisor + EventBus + LifecycleBus 收尾
```

## 6. 常见误解

| 误解 | 实际 |
|---|---|
| "市场扫描和 WS 推送只是喂料，不是工作流" | **它们是主工作流的数据入口层**——主工作流是 4 层端到端管道 |
| "市场扫描 / WS 推送 / 决策 / 执行是 4 条独立工作流" | 它们是**主工作流内部 4 层**，不是 4 条平行工作流 |
| "ENTRY_SIGNAL_TRIGGERED 是独立的入场决策链路" | 它是数据入口层 ③ 发出的事件，触发决策响应层 |
| "BUY 和 SELL 在不同链路" | 都在 `_decide_market_tick`，按"有/无持仓"分派 |
| "user_ws fill 会触发决策" | user_ws 是反馈层，只更新账户状态；下次 market_tick 自然读到新持仓 |
| "reconcile 是异常恢复" | reconcile 是**周期兜底**——主路径事件驱动碰不到的情况由它兜底 |
| "策略和工作流是两层" | 没有"策略"概念，整个系统就是一个 TradingWorkflow |
| "discovery 是入场决策的一部分" | discovery 是数据入口层 ①；universe 门禁在这里完成。入场决策在 QuantDecider 里发生 |
