# 体育扫尾策略完整接线设计

本文档用于约束体育扫尾能力的目标接线，避免为了单个盘口或单个测试先写局部最小实现。实现现状以代码和 `git log` 为准。

## 1. 目标边界

体育扫尾能力按完整目标形态建设，覆盖：

- `Totals`：总分盘口。
- `Moneyline`：胜负线盘口。
- `Spreads`：让分盘口。

三类盘口共享同一套业务对象、候选评估、执行权限、交易输出、恢复、展示和复盘口径。当前可以只开放部分自动执行权限，但代码结构不得按单一盘口写死。

## 2. 总体接线

目标接线如下：

```text
体育市场发现
-> market universe 精筛
-> 直播比分/阶段状态输入
-> orderbook 热状态输入
-> 体育扫尾候选模型
-> 候选评估与执行权限
-> size_entry / decide_entry
-> ExtensionDecision
-> TradingDecisionService
-> TradingService
-> RiskManager
-> OrderExecutor
-> outbox / audit / persistence（仅订单、成交、持仓和必要账户交易快照）
-> 管理台候选展示与复盘
```

必须保持：

- 策略只输出框架定义的 `ExtensionDecision`。
- 自动下单仍经过 `TradingService -> RiskManager -> OrderExecutor`。
- 人工确认也不能绕过风控和执行器。
- 候选评估拒绝原因不塞进 `Market.reject_reason`；`Market.reject_reason` 只表达 market 级 universe / 跟踪状态。

## 3. 文件级目标形态

### 3.1 `src/strategies/current/sports_tail/`

策略侧纯业务包（拆分为 types/parsing/leagues/slug/core/mlb/tennis/evaluator 子模块），负责：

- 直播比赛状态模型。
- 体育盘口模型。
- 候选模型。
- 候选评估结果。
- 执行权限枚举。
- 拒绝原因分类。
- `Totals`、`Moneyline`、`Spreads` 的统一评估入口。

约束：

- 不依赖 app、infra、worker。
- 不调用交易客户端。
- 不读写数据库。
- 不直接生成订单。

### 3.2 `src/strategies/current/config.py`

承载体育扫尾策略参数，负责：

- 三类盘口启用开关。
- 三类盘口执行权限。
- 价格上限。
- 流动性下限。
- 时间窗口、领先分差、安全垫等策略阈值。
- discovery 粗筛词和 tag。

约束：

- 体育策略参数不进入全局 `Settings`。
- 不为单个盘口新增临时环境变量。
- 默认配置必须能表达完整目标形态，而不是只表达当前启用盘口。

### 3.3 `src/strategies/current/universe.py`

负责 market 级筛选：

- 判断是否为体育市场。
- 判断盘口类型是否可解析为 `Totals`、`Moneyline` 或 `Spreads`。
- 判断 outcome 是否能映射到统一方向。
- 排除规则不清、文本无法解析、非白名单盘口。

约束：

- 不检查账户、持仓、盘口深度、价格滑点。
- 不做下单判断。
- 不把候选级拒绝原因写入 market 级状态。

### 3.4 `src/strategies/current/outcomes.py`

从固定主 outcome 解析升级为方向解析：

- `Totals`：解析 Over / Under。
- `Moneyline`：解析主队 / 客队 / 选手方向。
- `Spreads`：解析让分覆盖方向。
- 返回 token_id 和方向的稳定映射。

约束：

- 不继续假设主交易 token 永远是 `NO`。
- 解析失败必须返回可审计原因，不静默退化为任意 outcome。

### 3.5 `src/strategies/current/trading/`

负责把候选评估接入现有入场和退出 hook（拆分为 hooks/allocation/gates/matching/pricing/exit_overlay/risk_limits/helpers 子模块）：

- `size_entry()` 按统一评估结果决定预算是否可分配。
- `decide_entry()` 只有在候选评估通过且执行权限为自动执行时才返回 BUY。
- 非自动权限返回 SKIP，并在 metadata 中保留候选、权限和原因。
- 退出逻辑使用同一候选/持仓事实，不新增第二套退出来源。

约束：

- 不绕过 allocator、RiskManager、TradingService、OrderExecutor。
- 不在这里写直播状态数据获取逻辑。
- 不为 Totals 单独维护一条下单路径。
- sizing 和 entry decision 必须共享同一套体育候选原因字段，避免预算分配认为可买、入场决策再拒绝的双重事实。

### 3.6 `src/strategies/current/recovery.py`

负责体育 token 的恢复语义：

- 按实际持仓和 open orders 修复，而不是按固定主 token 修复。
- 取消异常 open BUY。
- 对未覆盖持仓补退出动作。
- 状态异常时暂停对应 market。

约束：

- 不把恢复动作变成自动新开仓入口。
- 不绕过 `TradingService` 和 `OrderExecutor`。

### 3.7 `src/strategies/current/tracking.py`

继续负责过滤后保留跟踪：

- 有持仓或挂单时继续跟踪。
- market 级异常状态可保留原因。
- 候选级评估结果不写进这里。

### 3.8 `src/strategies/current/strategy.py`

保持薄装配：

- 只导入和连接子模块。
- capabilities 增加体育扫尾能力描述。
- 不承载规则判断。

## 4. 框架层边界

### 4.1 通用契约与 app 接线

当前不修改交易输出契约：

- `ExtensionDecision`
- `ExtensionHooks`
- `TradingService`
- `RiskManager`
- `OrderExecutor`

原因：

- 体育扫尾策略最终仍可映射为 `skip / buy / sell / cancel / replace`。
- BUY/SELL 已能表达 token、价格、金额和份额。
- 风控和执行主链路已有强制门禁。

允许的 app 层接线：

- `TradingDecisionService / EntryPlanner` 可以透传 `metadata`，让事件输入、候选原因和执行权限进入 `ExtensionContext` 与 `EntryPlan`。
- `TradingDecisionWorker` 可以通过通用 `entry_metadata_provider` 在入场前补充运行时事实，例如直播比赛状态快照；provider 只返回 metadata，不在 worker 内做策略判断。
- 该 metadata 只用于策略输入、审计和展示，不在 app 层复制体育策略判断。

### 4.2 后续可能新增的输入能力

端到端体育直播能力需要新增或接入“输入/触发”能力：

- 直播比分。
- 当前阶段。
- 剩余时间。
- 盘口类型。
- 盘口线。
- 状态更新时间。

这些字段优先作为策略侧输入模型或端口读取结果，不应直接塞入 `domain.Market`。只有当多个策略都需要稳定依赖这些字段时，再考虑抽象为扩展 API 或通用 DTO。

当前推荐路径：

```text
外部直播状态源
-> infra/sports 适配与字段归一
-> sports_live_state_sync P2 worker
-> EntryMetadataStore
-> TradingDecisionWorker entry_metadata_provider
-> EntryPlanner metadata
-> ExtensionContext.metadata
-> sports_tail.live_game_state_from_metadata()
```

约束：

- provider 必须读取已经在内存中准备好的状态快照，不能在 P0 交易路径里执行阻塞 I/O。
- provider 不能判断是否下单、是否人工确认或是否拒绝；这些判断仍留在策略包。
- provider 失败时只应留下可审计 metadata 错误，不应把策略专属异常扩散成框架字段。

当前实现：

- `src/polymarket_trader/infra/sports/espn_client.py` 读取 ESPN scoreboard，并转换成 `domain.sports_live` DTO。
- `src/polymarket_trader/workers/sports_live_state_worker.py` 注册为 P2 scheduler job，写入 `EntryMetadataStore`。
- `src/strategies/current/live_state.py` 负责当前策略的 market/game 匹配和 `sports_tail_game` metadata 映射，并通过当前策略对象的 `match_sports_live_state` 可选 hook 注入 worker。
- `src/strategies/current/live_sample_validation.py` 负责离线校验 ESPN 真实样本、状态字段和 Polymarket market 匹配结果。
- `TradingDecisionWorker` 支持 `ENTRY_SIGNAL_TRIGGERED`，用于直播状态更新后基于最新 metadata 重放入场计划；该事件不改变风控和执行主链路。
- `/runtime`、`/workers`、`/metrics` 输出 `sports_live_sync` 快照，便于 supervisor / admin 查询。

## 5. 管理台与复盘接线

### 5.1 候选展示

候选展示应优先复用现有管理结构：

```text
route
-> AdminService
-> 候选快照 / 审计投影 / 策略 metadata
-> 前端 current extension 展示
```

当前实现：

- `EntryPlan.metadata` 保留事件输入、候选原因和执行权限，作为回放与管理展示的基础事实。
- `TradingDecisionWorker` 在 `SKIPPED` 和 `RISK_CHECK_*` 事件中输出 `plan_metadata`，用于串联候选、拒绝原因、执行权限和风控结果。
- 候选拒绝类 `SKIPPED` 事件只用于运行时审计展示，不进入数据库持久化 outbox，避免无套利候选持续落库。
- Persistence 审计记录只保留订单执行生命周期、成交、持仓和必要账户交易快照；候选 metadata 由运行时候选投影提供。
- Admin 审计查询返回事件 `payload`，前端审计页可查看 JSON 载荷。
- `GET /candidates` 从 registry、orderbook 热态和 `EntryMetadataStore` 构建候选投影。
- `GET /candidates` 只读取已形成运行时 metadata 的候选事实，或按显式 condition/token/slug 查询单个市场；管理台展示不能触发全量市场同步构建入场计划。
- 前端 `/candidates` 页面展示候选、直播同步状态、直播状态和确认返回。
- 前端只使用服务端 `confirmable` 字段决定确认入口是否可用，不复写策略判断。

### 5.2 人工确认

人工确认不是交易客户端直连入口。目标接线：

```text
候选详情
-> 人工确认操作
-> AdminService 受控操作
-> TradingDecisionService / TradingService
-> RiskManager
-> OrderExecutor
```

任何确认动作仍必须重新检查价格、流动性、状态和额度。

当前实现：

- `POST /candidates/confirm` 解析 market 与 token。
- AdminService 合并直播状态 metadata 与人工确认 metadata。
- TradingDecisionService 重新构建入场计划。
- TradingService 继续经过 RiskManager 与 OrderExecutor。
- 确认结果通过 review 返回，并发布低优先级审计事件。

### 5.3 复盘

复盘使用 `trace_id` 串联：

- 候选。
- 评估结果。
- 订单意图。
- 风控结果。
- 成交结果。
- 退出动作。
- 最终盈亏。

当前实现：

- `src/polymarket_trader/app/trade_replay.py` 按 `condition_id/token_id` 聚合 orders、fills、positions 和 audit events。
- `GET /trade-replays` 提供只读复盘查询，支持 `condition_id`、`token_id` 和 `trace_id` 过滤。
- 前端 `/replay` 页面展示买入/卖出成交、Data API PnL、结算状态、候选上下文和退出计划。
- `Position` 承接 Data API 的 `realized_pnl/cash_pnl/current_value/cur_price/redeemable` 等字段，管理台持仓页直接展示。

盈亏口径：

- 若 Data API position 返回 PnL 字段，复盘记录使用 `pnl.source=data_position`。
- 若 Data API PnL 缺失，则使用 fills 均价估算已实现盈亏，标记 `pnl.source=fills`。
- audit payload 只用于还原候选原因、直播状态和退出计划，不作为财务账本主数据源。
- `src/polymarket_trader/app/trade_replay_validation.py` 提供离线核对工具，可把 `/trade-replays` 响应与 Polymarket Data API 或页面导出的 positions JSON 做字段级对账。

核对命令：

```bash
PYTHONPATH=src python3 -m polymarket_trader.app.trade_replay_validation \
  --trade-replays /path/to/trade-replays.json \
  --positions /path/to/polymarket-positions.json
```

### 5.4 Moneyline / Spreads 校准

阈值校准属于当前策略能力，不进入框架 Settings：

- `src/strategies/current/calibration.py` 接收带标签的批量样本，复用 `evaluate_tail_opportunity()` 输出校准报告。
- 样本可同时包含 Moneyline、Spreads 和 Totals，并按 `policy_variants` 对比不同阈值组。
- 报告按盘口类型输出通过数、拒绝原因、TP/FP/TN/FN 和已标注样本盈亏。
- 命令行可运行：

```bash
PYTHONPATH=src python3 -m strategies.current.calibration <fixture.json>
```

## 6. 测试目标

测试必须验证目标实现，不倒逼局部最小实现。

完整实现后，测试应覆盖：

- 纯策略模型：三类盘口、执行权限、拒绝原因。
- universe：体育市场识别、盘口类型解析、outcome 解析失败。
- trading：非自动权限不下单，自动权限仍经过统一链路。
- recovery：不再依赖固定主 token。
- app 接线：`ExtensionDecision` 转 intent 后继续经过 RiskManager。
- 管理查询：候选、拒绝原因、执行权限、trace_id 不丢失。
- 前端：候选展示、过滤和人工确认入口类型检查。

## 7. 明确禁止

- 为 Totals 单独写一套下单流程。
- 为了通过当前测试写只覆盖样例的最小实现。
- 把体育专属字段直接塞进框架 domain 对象。
- 在 route、worker 或 Admin API 中复制策略判断。
- 把候选级拒绝原因混入 market 级 reject reason。
- 人工确认绕过 RiskManager 或 OrderExecutor。
