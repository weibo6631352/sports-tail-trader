# 新架构方案：工作流导向重组

**状态**：设计基准（实施前对齐）。完成后转入 CLAUDE.md / 删除。

## 0. 设计动机（不重复说）

- 目录按技术分层（domain / app / infra / runtime / workers）找代码要跳多目录
- 数据散在 4 个 store，市场全画像跨 store 拼，一对多关系靠 id 索引隐式
- 直播源订阅是隐式 polling（闭包推 sport），没有显式订阅注册表 + 优先级
- 校准混在 match 内部，错配能进 store
- prune callback 链 7 处散落易漏

## 1. 不可违反（继承 CLAUDE.md + 本轮新增）

继承：
- `RiskManager` 是任何下单前的强制门禁 → CLAUDE.md §3
- DB 仅审计，运行时不读 → §19.1
- 直播源 demand-driven，无 subscriber 不轮询 → §19.8
- 每个 store 单 writer → §19.3
- 校准失败不入 store → §18

本轮新增：
- **recovery 路径必经 OrderGateway**（不直连 order_executor）
- **直播源 inplay 优先级最高**（带 odd，是核心 edge 信号）
- **inplay 覆盖的 sport 只订 inplay，不订 livescore 冗余兜底**（prio 100 足够权威，多订一份就是浪费带宽和 §0 决策延迟）
- **DataGraph view 按需现拼**（无长期缓存，snapshot-and-release）
- **`_decide_position_action` 是有持仓时唯一决策入口**（_decide_market_tick 不直接出 SELL）
- **旧框架产物直接删，禁止扩展/复用/包装**（详见 §10）

## 3. 核心新组件

### 3.1 数据图层

- **`domain/graph.py`**：`EventView` / `MarketView` / `OutcomeView`（frozen dataclass，只读，无 IO）
- **`runtime/data_graph.py`**：`DataGraph`，跨 4 个扁平 store 按需聚合 view。snapshot-and-release：拿短锁拷贝引用 → 放锁 → 构造 view。无长期缓存。
- **`runtime/lifecycle_registry.py`**：market 进出的级联清理统一管。替代 7 处散落的 `register_prune_callback`。
  - `on_market_added(market)` → 通知 LiveSourceRegistry / OddsSubscriber 等订阅
  - `on_market_pruned(cid, token_ids)` → 通知 unsubscribe + 清 metadata + 清盘口

### 3.2 直播源订阅四件套（pipeline/ingest/live_source/）

```
registry.py            LiveSourceRegistry      引用计数订阅
poller.py              LiveSourcePoller        每 source 独立轮询
store.py               LiveStateStore          按 source 分桶
matcher.py             LiveSourceMatcher       market ↔ event 粗筛
calibrator.py          LiveSourceCalibrator    三角验证（team/time/league）
match_service.py       LiveStateMatchService   编排 matcher + calibrator，写 metadata store
subscription_policy.py SportsSubscriptionPolicy 决定 market 该订哪些 source
```

### 3.3 直播源优先级（新增）

`LiveSourceKey = (provider, sport)` 附带 priority：

| Source | Priority | 数据 | 触发订阅条件 |
|---|---|---|---|
| `goalserve_inplay` | **100** | 比分 + 实时 odd | inplay 覆盖的 sport（soccer/basket/tennis/volleyball/amfootball/esports/hockey/baseball） |
| `goalserve_livescore` | 50 | 纯比分 | **仅 inplay 不覆盖的 sport**（cricket/handball/rugby/golf/horse_racing/f1/motogp/boxing/mma 等） |
| `goalserve_pregame` | 10 | 赛前赔率 | 仅 `goalserve_pregame_enabled=true`，独立开关 |
| 其他 | 1 | 兜底 | 未来扩展 |

`MarketMetadataStore.write_live_state(cid, source, state, calibration)` 内部裁决：
1. 高 prio 总覆盖
2. 同 prio 取新 ts
3. 低 prio 仅在高 prio stale 时覆盖（保留低 prio 作 fallback 字段，比如 inplay 临时没数据时回退到 livescore 比分）

`SportsSubscriptionPolicy.required_sources(market)`（**每个 market 只订 1 个 primary live source**）：
- inplay 覆盖范围内的 sport → 订 inplay（**不订 livescore**——prio 100 已是权威，多订一份就是浪费带宽）
- inplay 不覆盖的 sport（cricket / handball / golf / horse_racing / f1 / motogp / boxing / mma / 等）→ 订 livescore
- pregame 是**独立维度**，按 settings 决定是否加订（不影响 primary 选择）

**单一 primary source 设计的 rationale**：
- 避免 §0 决策链路上重复拉同一场赛事的比分（同 sport 一次 inplay 拉拿到 N 场，再拉 livescore 是 100% 冗余）
- inplay 临时 stale（feed 短暂中断）的 fallback 不是"另外订 livescore"，而是**靠 inplay poller 自身的 stale 检测 + 退避重试**——这是 source 自身的健康问题，不该用业务订阅去补
- 真出现 inplay 长期故障，运维层处理（切断该 sport 后整体降级），不在订阅 policy 层加冗余

### 3.4 校准

`LiveSourceCalibrator` 三角验证：
- team name 双向 fuzzy 匹配（market slug 团队 ↔ event home/away）
- start_time 漂移检查（市场 game_start_time ↔ event start_time，≤ 5min）
- league 一致性（market category/tags ↔ event league）

不同 source 校准阈值不同：
- **inplay**：team match 严格 + start_time ±10min（含赔率，错配损失大）
- **livescore**：team match 严格 + start_time ±10min
- **pregame**：team match 严格 + start_time ±5min（一次匹配后不易复核）

任何一项失败 → `CalibrationResult.accepted=False`，**不写入 store**，落 `live_source_mismatch_recorded` audit 给运维查证。

## 6. position_heartbeat（薄盘兜底触发器，5s）

**不是旧遗留，是必要兜底**。问题场景：薄盘市场 orderbook 可能 30s+ 无 push，但持仓评估依赖的直播比分 / Goalserve 赔率 / math_lock 一直在变——必须有心跳触发器主动唤醒决策器，否则该止损/止盈时无人触发。

**实现**：scheduler 独立 job 周期 5s，遍历当前持仓 token，对每个 publish 一个**合成的** `ORDERBOOK_SNAPSHOT_UPDATED` 事件（payload 带 `synthetic=True` + `source=position_heartbeat`）。MarketTickWorker handler 内部 dedupe：同 token 5s 内有真实 orderbook 推送过 → 跳过合成 tick。

**为何复用 ORDERBOOK_SNAPSHOT_UPDATED 而不新增事件类型**：
- handler 路径单一，MarketTickWorker 只需订阅一种事件
- dedupe 逻辑天然（同 token / 同窗口）
- 心跳唤醒后跑的还是同一套 MTM 刷新 + decide_exit 逻辑，没必要分两套

**归属**：
- scheduler 注册：`runtime/scheduler.py`
- 心跳实现函数：`pipeline/decision/heartbeat.py`（决策层触发器）
- 命名：`position_heartbeat`（替代旧名 `position_exit_evaluator`——"evaluator" 听起来像独立组件，实际只是心跳信号源；"heartbeat" 已自带"周期评估"含义，无需 `_evaluation_` 中缀）

**迁移时一并删旧名**：现有代码里所有 `position_exit_evaluator` / `_publish_position_exit_evaluator_tick` / payload `source="position_exit_evaluator"` 全部 rename 到 `position_heartbeat`，不留双命名兼容（按 §10 原则）。audit_events 历史数据保留旧字符串，但新写入只用新名。

## 10. 旧框架产物处理原则（重组期间硬规则）

本重组是 **fresh-start 思路**，不是补丁式演进。遇到旧框架的任何遗留产物，**直接删，禁止扩展/复用/包装**。

### 10.1 什么算"旧框架产物"

- **旧命名**：散落在变量、函数、事件类型、scheduler job 名、audit_event reason 字符串、payload key 里的过渡命名（例：`position_exit_evaluator`、`SportsLiveStateWorker`、`live_state_match`、`market_tick_decide` 等等）
- **旧状态字段**：domain DTO / store / payload 里只为旧逻辑存在的字段，新架构不再写入也不再读
- **旧兼容旁路**：`if old_name in payload: ... elif new_name in payload: ...` 两路解析、`getattr(obj, "legacy_field", None)` duck-typing 兜底
- **旧 callback 链**：散落注册的 prune callback / lifecycle hook（统一到 `LifecycleRegistry` 后旧的全删）
- **旧 worker / 旧 client / 旧 scheduler job**：被新组件替代后整文件删，不在新代码里 import 也不留 stub
- **旧测试**：覆盖旧名/旧字段的测试随旧代码一起删，不"先注释等待清理"
- **旧文档**：runbook / docs / CLAUDE.md 里描述旧路径的段落同步删/改

### 10.2 处理动作（按这顺序）

遇到旧产物时：

1. **确认替代品已 ready**（新组件能完整覆盖旧职责，不留功能缺口）
2. **改所有引用方**到新名/新接口（一次 grep 跑全，不漏）
3. **删旧定义**（删文件 / 删函数 / 删字段 / 删 callback 注册）
4. **删旧相关测试 + 文档段落**
5. **`ruff check` 跑通**（确认无残留 import）
6. **启动后端冒烟**（确认运行时无 KeyError / AttributeError）

### 10.3 禁止行为

- ❌ 在新代码里 import 旧 module、调旧函数、读旧字段——即使"为了过渡"
- ❌ 在新组件里加 `# legacy: 兼容旧 X` 分支
- ❌ 加同义双命名（`new_name` + `_deprecated_old_name` 字段并存）
- ❌ 把旧逻辑"搬过来改一下"——应该**重写**，从工作流图重新推导该层的职责，不参考旧实现的内部结构
- ❌ 留 `TODO: 等彻底切到新架构后删` 之类标记——按 §10.2 顺序当场删干净
- ❌ 为了"减少 diff"保留旧文件名（即使内容改了）——文件名也要按新架构归位

### 10.4 唯一允许的过渡

**audit_events 表里历史数据的旧 reason 字符串保留不动**（DB 仅审计，按 CLAUDE.md §19.1，过去事件是历史事实不修改）。但新写入只用新名，admin API 查询时不做新旧映射——操作员自己看时间区分。

### 10.5 commit 自检

每个 commit 提交前：
- `git diff` 看是否引入了新的 `# legacy` / `# 过渡` / `# 兼容旧 X` 注释 → 有 → 重做
- grep 本次改动里的新文件，确认没 import 旧 module → 有 → 重做
- 删除的旧文件路径在 commit message 里列出（让 reviewer 一眼看到清理范围）

**核心心智**：每一步都按"新架构最终形态应该是什么样"写代码，旧的不是参考、不是基线、不是兼容对象——是要删除的废墟。

## 11. 性能监视（横切关注点）

### 11.1 设计原则

- **P0 路径 sync-collect + async-report**：决策热路径只做内存计数 / 时间戳记录（纳秒级），聚合 / 上报 / 落盘走 audit outbox 异步消费。**不允许 metrics 收集本身反向阻塞 P0**（呼应 CLAUDE.md §7 "P0 路径只允许同步执行"）
- **必须 actionable**：每个 metric 都要能回答"指标变差时我该做什么"。"为了好看加监控"禁止——观测点超载本身就是噪音
- **trace_id 贯穿全链路**：事件 → 决策 → 订单 → fill → audit 用同一 trace_id，运维查"某笔订单从哪条 ws 触发"能一键串起来
- **运行时快照默认暴露**：每个 worker / scheduler job / store 必须实现 `snapshot()` 方法，admin API 可拉。CLAUDE.md §8 已规定

P0 调用形态（举例）：

```python

    decision = quant_decide(ctx)

```

`perf_recorder.record` 必须是**零分配 context manager**（用 `__slots__` + 时间戳差），不能每次 new dict。

### 11.4 /health 端点

```

GET /health/live_sources       → 每个 LiveSourcePoller 的 last_success_ts / subscriber_count / lag

```

健康检查不是诊断工具，是**自动告警源**。判断逻辑写在 endpoint 内（如 `live_source last_success > 60s → status=degraded`），外部监控直接读 status 字段。

### 11.5 禁止

- ❌ 在 P0 路径 `await` metrics 上报
- ❌ metrics label 用高基数字段（如 condition_id / trace_id）—— label 只用维度有限的枚举（trigger / outcome / sport / source）
- ❌ 为单次 debug 加 metric 不删——debug 用 audit_event 临时打点，确认 actionable 再升级为 metric
- ❌ 把 audit_event 当 metric 用（audit 频率低 + 落 DB，metrics 高频 + 内存）

## 12. 后端 API 接口优化（横切关注点）

### 12.1 设计原则

- **agent 反应速度上界 = admin API 延迟**（§7.1）。所有 admin endpoint p95 < 100ms 是底线
- **所有读端点走 DataGraph view，不重复聚合**：portfolio / candidates / positions / market detail 等共用同一聚合层，避免每 endpoint 各自 join store
- **list 端点排序保不丢机会**（CLAUDE.md §17）：ready_to_trade / 直播中条目永远排前，截断时永不丢机会
- **agent 高频查询走 push 不走 poll**：admin WebSocket 推增量，agent 订阅一次后被动接收，不轮询

### 12.2 endpoint 三类划分

| 类 | 例子 | 性能要求 | 实现策略 |
|---|---|---|---|
| **运营查询**（agent / 操盘人高频读） | `/portfolio/exposure` `/candidates` `/positions` `/markets/{cid}` | p95 < 50ms | DataGraph view + 短 TTL 内存缓存（100ms）+ WS 增量 push |
| **审计查询**（操作员主动查历史） | `/audit-events` `/fills` `/orders/{id}/history` | p95 < 500ms 可接受 | 走 DB（§19.1 唯一允许 DB 读取场景），分页 + 索引覆盖 |
| **操盘动作**（人工触发受控操作） | `/positions/{cid}/force-exit` `/markets/{cid}/pause` `/orders/{id}/cancel` | 同步走 OrderGateway，落 audit | 严格鉴权 + 幂等 key + 走 RiskManager |

### 12.3 关键优化

**① 统一聚合层**

```
api/routes/portfolio.py
api/routes/candidates.py
api/routes/positions.py
api/routes/markets.py
        ↓ 全部读
api/aggregators/
├── portfolio_aggregator.py    # 基于 DataGraph 拼 PortfolioExposureView
├── candidate_aggregator.py    # 基于 DataGraph + decision history 拼 CandidateView
└── market_detail_aggregator.py
        ↓ 读
runtime/data_graph.py (DataGraph)
```

aggregator 是只读、无状态、可缓存的纯函数。删现有 `app/admin_*` 里各自的聚合代码。

**② 字段选择 + 详略分层**

```
GET /portfolio/exposure?level=summary    → 只返回总览（10 字段）
GET /portfolio/exposure?level=detail     → 完整（含每 token 的 orderbook / signals / 25 字段）
GET /markets/{cid}?fields=cur_price,shares  → 只返回指定字段
```

减少前端 / agent 反序列化成本。**summary 是默认**（避免无脑拉详情）。

**③ 短 TTL 内存缓存**

```python
# api/middleware/cache.py
@cache(ttl_ms=100, key=lambda req: f"{req.url.path}?{sorted(req.query_params.items())}")
async def get_portfolio_exposure(...): ...
```

只缓存运营查询类。100ms 窗口对 agent 看不出差别，但 burst 查询（同一 endpoint 10 次/s）只算 1 次。审计查询 + 操盘动作**禁止缓存**。

**④ WebSocket admin push**

```
WS /admin/stream
  client subscribe: {topics: ["portfolio", "candidates", "live_states"]}
  server push:      {topic, change_set}  // 只推增量
```

agent / 前端订阅一次后被动接收，不再每秒轮询。增量来源是已有 event_bus，加一个 admin_ws_publisher 桥接。

**⑤ 批量 endpoint**

```
POST /markets/batch         body: {condition_ids: [cid1, cid2, ...]}
POST /positions/batch       body: {condition_ids: [...]}
```

避免 agent N 次单调（呼应 §0.3 第 5 条）。一次响应 N 条记录。

**⑥ list 排序 + 大 limit**

CLAUDE.md §17 已规定。具体到 endpoint：

```python
# 默认 limit 大到不会截断（按 universe 真实规模设）
DEFAULT_LIMIT = 500
MAX_LIMIT = 2000

# 排序键（按机会优先级）
sort_key = lambda item: (
    not item.ready_to_trade,    # ready_to_trade 排前
    not item.is_live,            # 直播中排前
    -item.edge_bps,              # edge 大的排前
)
```

- 内部脚本 / agent prompt 中硬编码的旧 endpoint 路径同步改

## 13. 数据库与审计落盘优化（横切关注点）

### 13.1 设计原则

继承 CLAUDE.md §19.1（DB 仅审计，运行时不读 DB）。本节聚焦**写入侧**的纪律——
当前 audit_events 表存在高频重复写入 + 垃圾 payload 堆积问题，重构期间一并清理。

- **写入是付费操作**：每条 audit insert 都消耗 P3 worker CPU + 磁盘 IO + 后续查询代价。写之前问"这条记录将来真有人查吗"
- **同一事实的重复写入是浪费**：同一 condition 在 1 分钟内被拒 60 次（相同 reason）只需 1 条 + 计数
- **审计精度由"状态变化"驱动，不是由"时间"驱动**：状态没变就不需要新记录；状态变化必须记录（不漏审计断链）
- **schema 是为查询而设计的**：当前 schema 哪里查询慢、哪里 payload 浪费空间，重构时一并改

### 13.2 不值得写的"垃圾数据"（写入前 filter 掉）

| 类型 | 例子 | 处理 |
|---|---|---|
| **同 reason 短窗口反复评估** | 同 condition 在 60s 内被拒 N 次"orderbook_too_thin" | 第 1 次写完整记录，之后只更新 last_seen_at + count，不新建行 |
| **synthetic heartbeat 无决策动作** | `position_heartbeat` 5s tick 跑 decide_exit 返回 SKIP（无任何 state 变化） | 完全不写——decide_exit 返回 SKIP 且 metadata 与上次相同时直接 drop |
| **record-only 反复评估** | 明确 `record_only=True` 的市场（不交易）每 tick 评估一次 | 只在状态首次变化时写，之后状态稳定不写 |
| **payload 完全重复** | 同 trace_id 已记录过完全相同 payload（重传 / 重试触发） | 写入前用 (event_type, condition_id, payload_hash) 查内存 dedupe LRU，命中即 drop |
| **trivial 计数事件** | `discovery_tick_completed` 每 2s 一条 | 不进 audit_events——用 metrics counter 聚合即可（§11） |
| **debug log 性质** | `entered_function_X` / `loop_iter_n` 之类调试痕迹 | 写入前 reviewer 自检：将来 admin 会查这条吗？否则用 logger.debug 而非 audit |

### 13.3 写入侧 dedupe 策略

`PersistenceWorker`（消费 outbox）入口加 dedupe 层：

```python
# app/audit/persistence_worker.py
class AuditDeduper:
    """内存 LRU dedupe：(event_type, condition_id, payload_hash) 短窗口内只入库 1 次。
    
    命中重复时，更新现有行的 last_seen_at + count（UPDATE），不新建（INSERT）。
    P3 worker 同步操作，不影响主链路。
    """
    
    def should_persist(self, event: AuditEvent) -> PersistAction:
        # 返回 PersistAction.INSERT / UPDATE_COUNT / DROP
```

`PersistAction`：
- `INSERT`：首次见 → 完整插入新行
- `UPDATE_COUNT`：同 (event_type, condition_id, payload_hash) 短窗口内已有 → 只 UPDATE last_seen_at, occurrence_count
- `DROP`：明确判定为垃圾（如 SKIP + 状态无变化）→ 完全不写

dedupe 窗口（建议初始值，按实际数据观察调）：
- 拒绝类（reason 重复）：60s
- decide_exit SKIP：30s
- record-only 评估：300s
- payload-hash 完全重复：10s

### 13.4 schema 优化方向

**audit_events 表当前问题**（需要重构期间一并修）：

| 当前 | 优化目标 |
|---|---|
| `payload JSON`（PG JSON 类型） | `payload JSONB` —— 索引 + 查询性能 ×10，磁盘压缩 |
| 无 `occurrence_count` / `last_seen_at` 字段 | 加 `occurrence_count INT DEFAULT 1` + `last_seen_at TIMESTAMPTZ`，配合 13.3 dedupe |
| 无 `payload_hash` 字段 | 加 `payload_hash CHAR(16)`（短 hash 即可，dedupe 用），加唯一索引 `(event_type, condition_id, payload_hash, created_at::date)` |
| 单表千万行后查询慢 | 按 `created_at` **range partition by month**（PostgreSQL 原生分区），老分区 drop 一刀切 |
| 索引覆盖不足 | 至少补 `(event_type, created_at DESC)` + `(condition_id, event_type, created_at DESC)` + 高基数 reason 用部分索引 |
| 大 payload 字段全部回查 | 高频查询 endpoint（`/audit-events`）默认不返回 `payload`，加 `?include_payload=true` 才返回 |

**其他表**：

- `account_snapshots`：历史净值时间序列，按 `recorded_at` partition；高频时段（每 30s）→ 低频降采样（按时段聚合，5min 一条平均）
- `fills`：单笔 fill 必记，**不 dedupe**（金额事件不允许丢）；按 trade_id 唯一索引防重
- `orders`：order lifecycle 状态变化才写（CREATED / SUBMITTED / FILLED / CANCELLED），同一 order_id 中间无意义状态不写
- 旧的 `market_snapshots` / `position_snapshots`（如果还有）→ 评估是否被任何运营查询用到，没用直接 drop 表

### 13.5 retention 策略（自动清理）

每张表都要有 retention policy，避免无限增长：

| 表 | 保留 | 触发清理 |
|---|---|---|
| `audit_events` | 30 天（trade 类）/ 7 天（拒绝类）/ 1 天（heartbeat / synthetic 类） | 现有 `dead_records_purge` scheduler 扩展，按 event_type + age 分层 drop |
| `account_snapshots` | 90 天（降采样后），1 年（日级聚合归档） | 按月 partition + 老分区 detach + 归档 / drop |
| `fills` | 永久 | 不清（资金审计） |
| `orders` | 90 天 | 同 audit_events |

retention 配置统一放 `infra/db/retention_policy.py`，supervisor 拉起 cleanup job。

- 新增 event_type？→ 在 13.5 retention 表里加一行 + 在 13.2 垃圾判定里说清楚 dedupe 策略
