# 交易框架设计与边界

本文档是框架长期结构说明，描述当前代码的职责边界、运行链路和二次开发入口。
具体 API 字段以 FastAPI 自动生成的 `http://127.0.0.1:8000/docs`（Swagger UI）和 `/openapi.json` 为准，运行配置以 [`config.md`](./config.md) 为准，市场发现细节以 [`市场发现链路.md`](./市场发现链路.md) 为准。

## 1. 框架目标

框架提供一套可复用的 Polymarket 交易运行时：

- 发现市场并维护本地市场索引。
- 订阅 market / user 实时数据并维护内存状态。
- 把业务扩展决策转换成统一订单意图。
- 统一执行下单、撤单、改价和恢复动作。
- 提供审计、持久化、管理接口和状态校准能力。
- 让二次开发主要落在业务扩展目录，不改交易主链路。

框架不定义某个策略的 discovery 关键词、市场筛选语义、入场价格、退出价格、资金分配细则或订阅保留规则。这些规则属于 `src/strategies/` 下的业务扩展。

## 2. 分层结构

| 层 | 目录 | 责任 |
| --- | --- | --- |
| 接口层 | `src/polymarket_trader/api/` | Admin API、健康检查、参数校验、响应序列化 |
| 应用层 | `src/polymarket_trader/app/` | 编排用例，连接扩展、运行时状态和基础设施 |
| 领域层 | `src/polymarket_trader/domain/` | 市场、订单、成交、持仓、风控、状态机等通用模型 |
| 基础设施层 | `src/polymarket_trader/infra/` | Polymarket 客户端、数据库、outbox、持久化 |
| 运行时层 | `src/polymarket_trader/runtime/` | registry、event bus、scheduler、supervisor |
| worker 层 | `src/polymarket_trader/workers/` | 常驻后台任务和实时处理链路 |
| 扩展宿主层 | `src/polymarket_trader/app/extension_host/` | 业务扩展加载、重放工具、装配入口 |
| 应用端口层 | `src/polymarket_trader/app/ports/` | 面向业务扩展的应用层读取接口适配 |
| 扩展 API | `src/polymarket_trader/extension_api/` | 仓库内部业务扩展 SPI：hooks、上下文、决策对象、端口、manifest 和配置加载 |
| 扩展实现层 | `src/strategies/` | 具体业务扩展实现 |
| 前端管理台 | `frontend/` | 管理台前端、通用 UI 与业务扩展展示槽 |

依赖方向保持单向：`api / workers -> app -> domain`，`app -> infra / runtime / observability`，`infra -> domain`，`runtime -> domain`。

## 3. 运行时装配

装配入口是 `src/polymarket_trader/main.py`。

`build_runtime()` 组装：

- 配置与启动校验。
- Polymarket Gamma / CLOB / Data / WS 客户端。
- 事件总线和本地 outbox。
- 数据库 session factory 与持久化仓储。
- 市场状态、账户状态和指标注册表。
- 交易执行器、应用服务、worker、调度器和 supervisor。

运行时通过 `Settings.extension_module` 选择业务扩展包，并由 `app/extension_host/loader.py` 装配。`extension_config_path` 可指向扩展自己的外部配置文件。`main.py` 先创建 `ExtensionPorts`，再把 live orderbook reader 绑定到 `ports.market`。

框架只向扩展暴露市场、盘口、账户、预算等上下文，以及原始 `EntryCandidate` 候选列表；universe 判断、目标 token、入场价格、退出价格、深度和 spread 阈值都由扩展自己的 hooks 处理。

## 4. 核心链路

市场发现：

```text
ExtensionHooks.discovery_queries()
-> Gamma Events keyset API
-> MarketDiscoveryWorker
-> MarketService
-> ExtensionHooks.select_market()
-> MarketRegistry
-> MarketWsWorker subscription sync
```

交易判断：

```text
Market WS / User WS
-> EventBus
-> TradingDecisionWorker
-> TradingDecisionService
-> ExtensionHooks.size_entry() / decide_entry() / decide_exit() / decide_follow_up()
-> TradingService
-> RiskManager
-> OrderExecutor
```

恢复与校准：

```text
Scheduler / Admin API
-> ReconcileWorker
-> ReconcileService
-> ExtensionHooks.decide_recovery()
-> TradingService / Registry / AccountStateStore
```

发现和 Reconcile 共用终态跟踪策略：已经没有订阅价值且无账户敞口的 market 不进入
或退出 registry，包括 Polymarket 终态 `closed/resolved`、`end_date` 已过、以及策略通过
直播状态判定为 `ended/cancelled/retired` 的市场。清理动作会同时移除 `MarketRegistry`
记录和 `MarketWsWorker` 跟踪状态，下一轮 WS 订阅刷新不再包含对应 token；仍有持仓、
pending buy 或 open order 的市场必须保留跟踪。

持久化：

```text
OrderExecutor lifecycle event / user trade snapshot
-> LocalOutbox
-> PersistenceWorker
-> DatabasePersistenceRepository
-> PostgreSQL
```

市场发现、盘口快照、候选拒绝和运行时扫描状态不作为数据库写入事实；它们只更新内存 registry、运行时状态或低优先级运行事件。只有订单执行生命周期、成交、持仓和必要账户交易快照进入 outbox 持久化路径，避免全量市场扫描或无套利候选把数据库写入放大成热路径瓶颈。

## 5. 组件职责

接口层：

- route 只做参数校验、调用应用服务和响应序列化。
- route 不直接操作交易客户端。
- route 不直接读写运行时内部可变状态。
- `/runtime` 只暴露轻量运行态样本和全量计数，例如 `market_sample` 与 `registry.market_count`；完整市场列表由 `/markets` 分页提供。

应用层：

- `market_service.py` 负责市场发现、分类、注册和订阅相关编排；新发现的无敞口终态市场不进入订阅集合。
- `trading_decision_service.py` 把扩展决策桥接成订单意图。
- `trading_service.py` 是统一交易动作入口。
- `reconcile_service.py` 负责编排恢复和修复动作。
- `workers/reconcile/` 包内分子模块负责 reconcile 流程：authority refresh、diff 检测、action apply、订阅清理；只有无敞口终态市场才能从 registry 和 WS 跟踪中移除。
- `admin_service.py` 负责管理查询和受控操作。
- application 层不保存第二份业务真相，不硬编码某个策略的阈值语义。

领域层：

- 领域对象表达通用交易概念，不表达某个具体策略名字。
- 金额和价格使用 `Decimal`。
- 拒绝原因必须可审计，不能只返回 `False`。
- 字段命名保持单义，不保留长期别名或同义包装。

基础设施层：

- `infra/polymarket/` 适配 Gamma、CLOB、Data、WS 和执行客户端。
- `infra/db/` 负责 SQLAlchemy 持久化：`base.py` 收敛 Base / Mixin / helpers，`models/` 子包按聚合（market / orderbook / allocation / order / fill / position / account / audit / decision / outbox）分文件定义 ORM 类，`repositories/` 子包对应 repository 实现；`models/__init__.py` 重导出全部公共符号，老 import path 仍可用。
- `infra/outbox/` 负责本地 outbox 与事件投递。
- 外部 payload 必须先转成内部 DTO 再向上返回。

worker 层：

- worker 负责搬运消息和调度，不写策略规则。
- 交易主链路 worker 不能被持久化、日志或管理查询反向阻塞。

## 6. 业务扩展契约

扩展契约位于：

- `src/polymarket_trader/extension_api/hooks.py`
- `src/polymarket_trader/extension_api/context.py`
- `src/polymarket_trader/extension_api/decisions.py`
- `src/polymarket_trader/extension_api/ports.py`（含 `MarketReadPort` / `OrderbookReadPort` /
  `AccountReadPort` / `HistoryReadPort` / `RuntimeReadPort` / `ConfigReadPort` /
  `TelemetryPort` / `ClockPort` / `LifecycleBus` / `ParameterPort`——
  `ParameterPort` 让策略在 hook 内读 runtime override 值，默认回退到 frozen config）
- `src/polymarket_trader/extension_api/manifest.py`

业务扩展通过 manifest 暴露 `BusinessExtension`，并提供 `ExtensionHooks` 实现：

- `discovery_queries()` / `discovery_queries_for_live_games()`
- `select_market()`
- `match_live_state()` —— 把直播源 game 状态匹配到具体 market
- `size_entry()`
- `decide_entry()`
- `decide_exit()`
- `decide_recovery()`
- `decide_follow_up()`
- `should_keep_tracking()`
- `build_filtered_tracking_market()`

扩展输出框架定义的决策对象，不直接调用交易客户端。`ExtensionDecision` 必须显式给出 `token_id`、`action`、`order_type`、`price`、`size` 等交易形状；框架不默认把某个 market 的某个 outcome 当成唯一目标。

默认示例扩展位于 `src/strategies/current/`：

- `manifest.py`：扩展 manifest。
- `strategy.py`：扩展入口和 hooks 实现。
- `config.py`：策略参数常量和扩展配置。
- `universe.py`：市场筛选。
- `trading/`：分配、入场、退出（hooks/allocation/gates/matching/pricing/exit_overlay/risk_limits/helpers）。
- `recovery.py`：恢复决策。
- `tracking.py`：订阅保留规则。

## 7. 状态真相与并发

状态真相优先级：

1. Polymarket 实时事件与权威快照。
2. 本地内存状态。
3. PostgreSQL 审计与快照。

执行规则：

- 交易实时判断依赖内存状态。
- 权威修正依赖 WS 和 REST。
- 数据库用于查询、审计、复盘和恢复参考，不作为交易唯一真相来源。
- 交易主链路优先级最高。
- 阻塞 I/O 和 CPU 密集任务离开交易主事件循环。
- 持久化、报表和 Admin 查询不能占用交易执行资源。
- 队列有容量上限、可观测性和降级路径。
- 高频盘口事件的削峰在队列边界处理；同一 token 尚未消费的盘口事件只保留最新事实，不在交易决策 worker 内按时间静默丢弃已出队事件。

## 8. Admin API 与前端管理台

Admin API 承载三类职责（路由明细以 `/openapi.json` 为准）：

**只读查询与可观测性**：
- 健康检查、运行态、worker 状态、metrics 与延迟分位数。
- 市场、订单、成交、持仓、组合、审计、分配、outbox 数据查询。
- 单笔交易 timeline 复盘（合并 decisions / orders / fills / audit / reconcile）。
- 分析视图：funnel、rejections、execution-quality、edge-realization、
  calibration（含 Brier / log-loss）、missed-opportunities、risk-rejections
  聚合、PnL breakdown、risk-metrics（drawdown / Sharpe-like）、operator
  intervention 聚合。
- 历史盘口、体育实时事件、reconcile diff、settlement 等结构化事件视图。

**受控人工操作**：
- 人工 reconcile / order replace / order cancel / position force-exit。
- 人工 pause / resume trading（账户级与单市场）。
- 人工录入 settlement 结果（给 calibration 提供 ground truth）。
- candidate confirmation、live state upsert。

**实时调参**：
- `GET /parameters` / `PUT /parameters/{scope}/{key}` / `DELETE /parameters/{scope}/{key}`
  覆盖白名单内的风控阈值或策略参数。覆盖只活在进程内存（重启即丢），每次变更
  通过 `PARAMETER_OVERRIDE_APPLIED` 事件落 audit_events。
- `POST /operations/parameter-sweep` 对历史决策做参数候选笛卡尔积回放，
  read-only 算 hypothetical PnL。

Admin API 不承载策略计算、自动下单入口或交易客户端直连——所有受控人工动作仍走
TradingService -> RiskManager -> OrderExecutor 主链路。

前端管理台位于 `frontend/`：

```text
frontend/src/
  app/          # 应用壳体、路由、provider、AppShell
  core/         # HTTP client、SSE 连接、query key、时间窗口、observability
  shared/       # 通用 UI、表单 / 表格 / 图表预设、格式化工具
  features/     # live / investigate / analytics / markets / ops / system 六大区
  strategy/     # 策略 bundle 注册入口 (strategy/current/) + StrategyShell
  styles/       # Mantine theme + CSS tokens
```

前端边界：

- 浏览器统一通过 `/api/*` 访问后端，不直接接 Polymarket。
- 通用页面只消费 Admin API 和扩展展示接口，不复写业务扩展判断逻辑。
- `shared/` 不依赖 `features/`。
- `features/` 只能依赖 `shared/`、`core/` 和扩展展示接口。
- `strategy/current/` 通过 StrategyBundle 协议暴露 routes / widgets / paramSchema 钩子，
  不能反向 import `features/` 或直接持有 apiClient。

## 9. 配置边界

框架配置由 `.env` 和 `Settings` 管理，例如：

- Polymarket host / WS 地址。
- 钱包和交易凭据。
- 数据库。
- 线程池、进程池和队列大小。
- 超时、重试和通用风控上限。
- `EXTENSION_MODULE` 与可选 `EXTENSION_CONFIG_PATH`。

策略参数不属于框架公共契约。默认示例扩展通过 `src/strategies/current/config.py` 和自己的配置加载方式管理业务参数。

**Runtime override 层（`ParameterStore`）**：

`Settings` 与策略 frozen config 都是启动期不变量；运行时探索性调参走独立的
`src/polymarket_trader/app/parameter_store.py`：

- 白名单内的 `(scope, key)` 才能 PUT 覆盖，避免误调密钥 / 不安全字段。
- 框架侧消费走 `parameter_store.get('settings', key, default=settings.X)`；
  `TradingDecisionWorker` 的 max_order_usdc / max_market_usdc / max_total_usdc
  等 properties 已接入。
- 策略侧消费走 `ports.parameter.get('strategy', key, default=cfg.X)`；
  默认扩展用 `strategies/current/parameter_overrides.py` 的
  `active_ports_scope` ContextVar 让深层 helper 不必把 ports 一路 plumb。
- 每次写入通过 `PARAMETER_OVERRIDE_APPLIED` 事件落 audit_events，保留
  `previous / new / operator / applied_at`。
- 覆盖**重启即丢**——长期固化仍走 `.env` 改 Settings 或策略 config 文件。

## 10. 手续费工具

手续费纯计算逻辑位于 `src/polymarket_trader/domain/fees.py`：

- `calculate_trade_fee(...)`
- `build_taker_fee_preview(...)`

公式：

```text
fee = C * feeRate * p * (1 - p)
```

对应关系：

- `C = size_shares`
- `p = price`
- `feeRate = fee_rate_bps / 1000`

`build_taker_fee_preview(...)` 使用当前 market 和 orderbook 生成管理台展示用预估：

- `basis_size_shares = 100`
- 买单取 `best_ask`
- 卖单取 `best_bid`
- 没有盘口时返回 `None`

`fee_preview` 是热态派生视图，不是 `Market` 静态字段，也不落库。

## 11. 二次开发入口

按改动归属定位文件：

- 改策略规则：优先改 `src/strategies/current/`
- 改扩展契约：改 `src/polymarket_trader/extension_api/`
- 改交易编排：改 `src/polymarket_trader/app/`
- 改接入或存储：改 `src/polymarket_trader/infra/`
- 改运行时调度：改 `src/polymarket_trader/workers/` 或 `src/polymarket_trader/runtime/`
- 改人工查询和操作：改 `src/polymarket_trader/api/`
- 改管理台通用页面：改 `frontend/src/features/`
- 改管理台策略展示：改 `frontend/src/strategy/current/`

常见错误：

- 在 route 里写交易逻辑。
- 在 worker 里复制 discovery 或 strategy 业务判断。
- 在 framework 层加入当前策略专属字段或阈值。
- 在 domain 层加与当前扩展强绑定的字段。
- 为了减少改动在框架层保留同义字段、重复别名或多套命名包装。
- 让数据库、持久化、日志或报表路径决定交易热路径是否能继续运行。
