# 体育扫尾策略开发实施计划

本文档记录当前开发执行计划。计划会随实现推进更新，但每次变更都应保持可追溯、可验证。

## 1. 开发目标

在不改交易主链路的前提下，按完整目标形态建设体育扫尾策略能力：

- 覆盖 `Totals`、`Moneyline`、`Spreads` 三类盘口。
- 三类盘口共用候选、评估、风控、执行权限和退出口径。
- 当前先构建策略包内的纯业务模型和评估规则，再接入运行时上下文、管理台和交易执行。

## 2. 实施原则

- 先明确完整目标边界，再写测试验证目标实现；不为了中间最小实现先写测试。
- 先做纯业务规则，再接运行时和外部数据。
- 策略差异留在 `src/strategies/current/`。
- 通用交易链路、风控和执行器不为单个策略开旁路。
- 每个开发切片完成后更新 [`开发进度.md`](./开发进度.md)。

## 3. 任务拆分

### 任务 1：完整接线设计固化

目标：

- 在代码实现前固化文件级目标接线。
- 明确策略包、框架、管理台和复盘边界。

计划文件：

- 新增 `docs/体育扫尾完整接线设计.md`
- 更新 `docs/README.md`
- 更新 `README.md`

验收：

- 明确 `sports_tail/config/universe/outcomes/trading/recovery/tracking/strategy` 的目标职责。
- 明确暂不改通用输出契约。
- 明确候选展示和人工确认不绕过主链路。

### 任务 2：策略包目标模型实现

目标：

- 在策略包内一次性实现完整目标模型。
- 覆盖 `Totals`、`Moneyline`、`Spreads`，不只服务单一测试样例。

计划文件：

- 新增 `src/strategies/current/sports_tail.py`
- 修改 `src/strategies/current/config.py`
- 修改 `src/strategies/current/outcomes.py`
- 修改 `src/strategies/current/universe.py`

验收：

- 三类盘口共用同一候选和评估结果对象。
- 三类盘口都有执行权限、拒绝原因和 token 方向解析。
- 策略参数留在策略配置，不进入全局 `Settings`。

### 任务 3：交易 hook 接入

目标：

- 将完整候选评估接入现有 `size_entry()`、`decide_entry()`、`decide_exit()`。
- 只在自动执行权限下输出 BUY。
- 非自动权限输出 SKIP 和可审计 metadata。

计划文件：

- 修改 `src/strategies/current/trading.py`
- 修改 `src/strategies/current/recovery.py`
- 修改 `src/strategies/current/strategy.py`

验收：

- 不产生绕过 `TradingService / RiskManager / OrderExecutor` 的路径。
- 固定 `NO` 主 token 假设被替换为候选方向 token。
- 恢复逻辑按实际持仓和 open orders 修复。

### 任务 4：候选展示与审计投影

目标：

- 让管理台能展示候选、执行权限、拒绝原因和 trace_id。
- 保持 API route 只做查询和受控操作，不写策略判断。

计划文件：

- 优先扩展 `frontend/src/extensions/current/extension.tsx`
- 必要时新增 app/admin 只读查询或复用 audit payload
- 同步更新 `docs/api.md` 和 `frontend/README.md`

验收：

- 候选级拒绝原因不写入 `Market.reject_reason`。
- app 层 `EntryPlan.metadata` 保留事件输入、候选原因和执行权限，便于回放和管理台复用。
- 人工确认入口不直连交易客户端。
- `trace_id` 能串联候选、订单、风控、成交和退出。

### 任务 5：完整测试与回放验证

目标：

- 用测试验证目标实现，而不是倒逼局部最小实现。
- 完整覆盖策略、接线、恢复、管理查询和前端类型。

计划文件：

- `tests/strategies/current/test_sports_tail.py`
- `tests/strategies/current/test_universe.py`
- `tests/strategies/current/test_trading.py`
- `tests/strategies/current/test_recovery.py`
- 必要时补 app/admin 和前端测试

验收：

- 三类盘口通过/拒绝场景完整。
- 非自动权限不会下单。
- 自动权限仍经过风控。
- 状态缺失、价格过高、流动性不足、规则不清均可审计。

## 4. 当前执行状态

已完成：

- 任务 1：完整接线设计固化。
- 任务 2：策略包目标模型实现。
- 任务 3：交易 hook 接入。
- 任务 4 的基础审计接线：`TradingDecisionService / EntryPlanner / replay / worker` 已能传递事件 metadata，`EntryPlan.metadata` 和审计 payload 已能保留候选原因和执行权限。
- 直播状态输入的通用接入点：`TradingDecisionWorker.entry_metadata_provider` 已能在入场前补充运行时 metadata。
- 任务 4 的候选管理接线：
  - Runtime 已有 `EntryMetadataStore` 保存直播状态 metadata。
  - `GET /candidates`、`GET/POST /candidates/live-states` 和 `POST /candidates/confirm` 已接入 AdminService。
  - 前端 `/candidates` 页面已展示候选、直播状态和人工确认入口。
  - 人工确认会重新构建入场计划，并经过 `TradingService -> RiskManager -> OrderExecutor`。

下一步：

- 接入外部直播状态源的 infra 适配器和字段归一。
- 按真实输入补状态新鲜度、异常状态和回放验证。
- 根据实盘复盘结果校准 Moneyline / Spreads 阈值和执行权限。
