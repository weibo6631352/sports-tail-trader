# 体育直播状态输入设计

本文档约束体育扫尾策略所需的比分、阶段、剩余时间等直播状态如何进入交易判断。

## 1. 目标

体育直播状态是策略运行时输入，不是 Polymarket market 的静态属性。目标链路是：

```text
外部直播状态源
-> infra 适配与字段归一
-> runtime 内存快照
-> TradingDecisionWorker entry_metadata_provider
-> EntryPlanner metadata
-> ExtensionContext.metadata
-> sports_tail.live_game_state_from_metadata()
-> decide_entry()
```

## 2. 数据形态

策略当前消费的 metadata 字段为 `sports_tail_game`，结构应至少包含：

- `league`
- `home_name`
- `away_name`
- `home_score`
- `away_score`
- `period`
- `seconds_remaining`
- `status`
- `observed_at`

字段语义：

- `status` 使用策略侧 `LiveGameStatus` 可识别的值，例如 `live`、`paused`、`ended`。
- `observed_at` 是状态源观测时间，用于新鲜度判断。
- `seconds_remaining` 缺失时，Totals Over 已锁定场景仍可判断；Moneyline、Spreads 和 Under 近锁定场景必须拒绝。

## 3. 接入边界

### 3.1 Infra

Infra 负责外部协议适配：

- 拉取或接收直播比分数据。
- 将外部字段转换成内部快照。
- 处理外部 API 限流、失败、重试和原始 payload 脱敏。

Infra 不负责：

- 判断是否套利。
- 判断是否下单。
- 写入策略阈值。

### 3.2 Runtime

Runtime 负责保存轻量内存快照：

- 当前使用 `EntryMetadataStore` 按 `condition_id`、`market_slug` 或 `event_slug` 建索引。
- 暴露无阻塞读取接口。
- 通过 `GET /candidates/live-states` 暴露快照、来源和最后更新时间。

Runtime 不负责：

- 把体育字段塞进 `domain.Market`。
- 在热路径里执行阻塞 I/O。
- 替代策略判断。

### 3.3 Worker

`TradingDecisionWorker` 只在入场前调用通用 `entry_metadata_provider`，并把返回值合并到事件 metadata：

```text
event.payload + provider metadata -> build_entry_plan(metadata=...)
```

约束：

- provider 只能返回 metadata。
- provider 不能解析体育规则、执行权限或拒绝原因。
- provider 失败时留下可审计错误，策略在缺少有效直播状态时拒绝入场。

当前运行时装配：

- `build_runtime()` 创建 `EntryMetadataStore`。
- `TradingDecisionWorker.entry_metadata_provider` 通过 `condition_id`、`token_id` 或 `market_slug` 解析 market，再读取对应 metadata。
- provider 返回值会与 `event.payload` 合并后进入 `EntryPlanner`。

### 3.4 Strategy

策略负责最终解释：

- 从 `ExtensionContext.metadata["sports_tail_game"]` 读取状态。
- 判断状态是否 live。
- 判断状态是否过期。
- 判断比分、盘口线、方向和剩余时间是否满足候选规则。
- 输出 `ExtensionDecision` 和候选 metadata。

## 4. 审计与展示

直播状态输入必须可复盘：

- `EntryPlan.metadata` 保留 provider 合并后的输入事实。
- `SKIPPED` 和 `RISK_CHECK_*` 事件输出 `plan_metadata`。
- Admin 审计查询返回 `payload`。
- 前端审计页可查看 JSON 载荷。
- 前端候选页可查看服务端候选、直播状态和人工确认返回。

候选展示与人工确认规则：

- `GET /candidates` 展示服务端候选投影。
- `POST /candidates/confirm` 提供人工确认入口。
- 前端只使用服务端返回的 `confirmable` 决定是否允许确认，不复写策略判断。

直播状态写入规则：

- `POST /candidates/live-states` 写入 `sports_tail_game`。
- `condition_id`、`market_slug` 或 `event_slug` 至少提供一个。
- API 不触发下单，也不改变策略阈值。

## 5. 失败策略

缺少直播状态时：

- 当前体育扫尾策略返回 `missing_live_game_state`。
- 不创建 BUY。
- 发布可审计 SKIPPED 事件。

状态过期时：

- 返回 `stale_game_state`。
- 不创建 BUY。
- 保留状态更新时间与当前判断时间，便于复盘。

状态异常时：

- 暂停、延期、取消、争议、退赛和未知状态默认拒绝。
- 拒绝原因必须进入候选 metadata 或审计 payload。

## 6. 禁止事项

- 不把 `sports_tail_game` 或比分字段加入 `domain.Market`。
- 不在 `MarketWsWorker` 中硬编码体育直播状态。
- 不在 `TradingDecisionWorker` 中写体育策略判断。
- 不让 discovery 的 universe 判断替代入场前直播状态门禁。
- 不通过 `.env` 或全局 `Settings` 承载动态比分。
- 不在 P0 交易路径里同步请求外部直播 API。
