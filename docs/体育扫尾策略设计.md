# 体育扫尾策略目标设计

本文档承接 [`业务需求.md`](./业务需求.md)，把“会操作电脑的金融分析师”的业务动作抽象成可长期演进的目标设计。本文只描述目标形态、职责边界和业务对象，不约束具体代码实现细节。

## 1. 设计目标

- 一次性面向完整目标形态建模，覆盖 `Totals`、`Moneyline`、`Spreads` 三类体育扫尾机会。
- 三类盘口使用同一套候选发现、确定性判断、价格评估、风控、执行权限、退出和审计口径。
- 当前可以只启用部分自动交易权限，但业务模型不能按单一盘口写死流程。
- 任何跳过、拒绝、降级和退出动作都必须保留可审计原因。

## 2. 总体链路

目标业务链路如下：

```text
直播体育市场
-> 比赛状态与盘口状态
-> 扫尾候选
-> 确定性评估
-> 价格与流动性评估
-> 风控与执行权限
-> 买入 / 提醒 / 人工确认 / 跳过
-> 持仓跟踪与退出
-> 审计与复盘
```

该链路必须对所有策略类型统一生效，不允许 `Totals`、`Moneyline`、`Spreads` 分别维护独立交易主流程。

## 3. 核心业务对象

### 3.1 直播比赛

直播比赛表示正在进行中的体育事件，至少需要表达：

- 比赛名称、联赛、队伍或选手。
- 当前比分。
- 当前阶段，例如节、局、盘、半场、补时。
- 剩余时间或进度。
- 比赛状态，例如直播中、暂停、延期、结束、争议、退赛。
- 状态更新时间。

直播比赛状态是候选判断的基础。状态不清楚、不新鲜或存在冲突时，候选必须降级或跳过。

### 3.2 体育盘口

体育盘口表示可交易的具体市场，至少需要表达：

- 盘口类型：`Totals`、`Moneyline`、`Spreads`。
- 盘口线，例如 `Over 4.5`、让分线或胜负结果。
- 目标结果，例如 Over、Under、主队、客队、让分覆盖方。
- 当前买入价、卖出价、价差和可成交深度。
- 交易量和流动性状态。
- 结算规则摘要。

盘口类型不同，但都必须被转成统一候选对象后再进入评估。

### 3.3 扫尾候选

扫尾候选表示一个可能值得交易的机会，至少需要包含：

- 关联比赛。
- 关联盘口。
- 候选类型：总分、胜负线、让分。
- 当前比分和盘口线。
- 候选方向。
- 候选原因。
- 主要风险。
- 当前建议动作。

候选只是“值得进一步检查”，不是下单信号。任何候选都必须继续经过价格、流动性、风控和执行权限检查。

### 3.4 执行权限

每个策略类型和盘口可以配置不同执行权限：

- `只记录`：只进入日志和复盘，不提醒。
- `只提醒`：展示机会，但不自动下单。
- `人工确认`：需要人工确认后才能下单。
- `自动执行`：满足全部条件后自动下单。

执行权限用于控制上线节奏，但不改变候选、评估和风控模型。

## 4. 策略类型设计

### 4.1 Totals 总分扫尾

目标：

- 捕捉当前比分已经让总分结果事实成立，或结果接近锁定但价格仍有折价的机会。

主要候选：

- 当前总分已经超过 Over 盘口线。
- 当前总分距离盘口线很远，剩余时间不足以合理改变 Under 判断。

默认业务偏好：

- 优先考虑已经事实成立的 Over。
- 对仍依赖剩余时间推演的 Under 保持更高门槛。

### 4.2 Moneyline 胜负线扫尾

目标：

- 捕捉比赛末段领先方胜率已经极高，但价格仍未充分反映的机会。

主要候选：

- 比赛进入末段。
- 领先优势明显。
- 当前价格相对分析判断存在折价。

默认业务偏好：

- 小比分领先、剩余时间较多、存在加时或特殊规则时跳过。
- 默认执行权限应比 Totals 更保守。

### 4.3 Spreads 让分扫尾

目标：

- 捕捉比赛末段让分结果接近锁定，但价格仍有折价的机会。

主要候选：

- 剩余时间少。
- 领先差距相对盘口线有足够安全垫。
- 垃圾时间得分不易改变让分结果。

默认业务偏好：

- 不做比赛早中期让分。
- 让分结果仍容易被最后得分改变时跳过。

## 5. 统一评估维度

每个候选必须按同一组维度评估：

- `确定性`：结果是否已经事实成立，或是否达到高确定性。
- `价格折价`：买入价格是否低于分析判断的合理价格。
- `流动性`：目标金额是否可以按预期价格成交。
- `成本覆盖`：预期收益是否覆盖费用、滑点和资金占用。
- `状态可靠性`：比分、阶段、盘口和比赛状态是否清晰及时。
- `规则风险`：结算规则是否明确，是否存在取消、退赛、延期等风险。
- `额度风险`：单笔、单场、单联赛、单日风险额度是否可用。
- `执行权限`：当前策略是否允许自动执行，还是只能提醒或人工确认。

任何维度不满足时，都必须给出明确拒绝原因。

## 6. 退出设计

买入后不要求必须等待结算。退出动作包括：

- 价格回归到目标价后提前卖出。
- 比赛即将结束且结果稳定时等待结算。
- 比赛状态异常时停止加仓并评估减仓。
- 数据冲突、盘口关闭或流动性消失时进入人工处理。

退出判断应与入场判断共用比赛状态、盘口状态和风控信息，不能另建一套事实来源。

## 7. 审计与复盘

每个候选、决策和交易结果都必须可复盘：

- 候选出现时间。
- 比赛、盘口、比分、阶段和价格。
- 判断理由。
- 拒绝或通过的风控项。
- 执行权限。
- 买入、退出和结算结果。
- 实际盈亏。

复盘目标不是只统计收益，还要识别误判来源：状态延迟、规则理解错误、流动性不足、价格回归不达预期或风控过宽。

## 8. 不做的事

- 不预测未开赛比赛。
- 不把某个策略写成绕过统一风控和执行链路的独立流程。
- 不在人工操作入口直接下单。
- 不为单个盘口增加长期专属字段、状态或配置到框架层。
- 不在规则不清楚、状态不可靠或流动性不足时强行交易。
