# 体育扫尾策略二次开发计划

本文档承接 [`业务需求.md`](./业务需求.md) 和 [`体育扫尾策略设计.md`](./体育扫尾策略设计.md)，用于指导后续开发工作。计划目标是一次性按完整目标形态设计，分批启用交易权限，避免围绕单个盘口补丁式开发。

## 1. 开发原则

- 先建立统一业务模型，再接入具体策略类型。
- `Totals`、`Moneyline`、`Spreads` 共享候选、评估、风控、执行和退出链路。
- 策略差异留在策略包内，通用运行能力留在框架。
- 每个开发单元都要能独立验证，不依赖临时旁路。
- 自动下单相关改动必须覆盖拒绝原因、风控、幂等和异常状态测试。

## 2. 里程碑 A：业务对象与文档对齐

目标：

- 把业务需求中的比赛、盘口、候选、评估、执行权限和退出结果整理成统一术语。
- 明确哪些对象属于策略包，哪些对象属于框架通用契约。

交付物：

- 更新策略侧文档，说明三类盘口共享同一候选模型。
- 明确执行权限枚举：只记录、只提醒、人工确认、自动执行。
- 明确拒绝原因分类：状态、价格、流动性、规则、额度、权限。

验收：

- 文档中不再出现只服务单一盘口的主流程描述。
- 后续开发者能从文档判断一个新增字段应该放在策略包还是框架契约。

## 3. 里程碑 B：候选发现与统一评估

目标：

- 将直播体育市场统一转成扫尾候选。
- 所有候选先进入评估，再决定提醒、人工确认、自动执行或跳过。

开发范围：

- 在策略包内新增体育扫尾候选识别逻辑。
- 候选对象需要包含比赛、盘口、比分、阶段、方向、理由和主要风险。
- 评估结果需要包含通过/拒绝、评分或等级、拒绝原因和建议动作。

验收：

- `Totals`、`Moneyline`、`Spreads` 都能产出同一种候选结果。
- 跳过候选时必须能说明原因。
- 没有任何候选可以绕过统一评估直接进入下单。

## 4. 里程碑 C：比赛状态与盘口状态接入

目标：

- 为候选评估提供可靠的直播比分、比赛阶段、盘口价格和流动性信息。

开发范围：

- 接入直播体育状态。
- 确认比分、阶段、状态更新时间和异常状态表达方式。
- 接入盘口价格、价差、可成交深度和交易量。
- 状态过期、冲突或缺失时，候选必须降级或拒绝。

验收：

- 每个候选都能展示状态更新时间。
- 状态不新鲜时不会自动下单。
- 比分或盘口信息缺失时能给出明确拒绝原因。

## 5. 里程碑 D：三类策略规则

目标：

- 在统一评估框架下分别实现三类盘口规则。

开发范围：

- `Totals`：识别总分已打穿和接近锁定场景。
- `Moneyline`：识别比赛末段领先方扫尾场景。
- `Spreads`：识别比赛末段让分接近锁定场景。
- 每类规则只输出候选和理由，不直接调用交易执行。

验收：

- 三类规则都能独立关闭或开启。
- 三类规则都能配置执行权限。
- 新增盘口规则不需要修改交易主链路。

## 6. 里程碑 E：风控与执行权限

目标：

- 将候选转成可执行动作前，统一检查资金、额度、价格、流动性和权限。

开发范围：

- 单笔、单场、单联赛、单日额度。
- 连续亏损暂停。
- 价格上限和收益下限。
- 流动性下限和滑点上限。
- 策略执行权限：只记录、只提醒、人工确认、自动执行。

验收：

- 自动执行前必须经过风控。
- 人工确认不能绕过风控。
- 同一比赛多个盘口不能重复暴露不可控风险。
- 达到亏损上限后停止新开仓。

## 7. 里程碑 F：退出、恢复与异常处理

目标：

- 买入后持续跟踪机会，支持提前卖出、等待结算、异常停止和人工处理。

开发范围：

- 价格回归目标后的退出。
- 比赛即将结束时的持有判断。
- 状态异常、盘口关闭、流动性消失时的降级。
- 断线、订单异常、成交不完整时的恢复。

验收：

- 买入后必须有退出计划。
- 异常状态不允许继续加仓。
- 恢复动作必须记录原因和结果。

## 8. 里程碑 G：管理台与复盘

目标：

- 让人工分析师能看到电脑助手正在观察什么、为什么行动或跳过。

开发范围：

- 候选列表。
- 当前执行权限。
- 通过/拒绝原因。
- 当前持仓、退出计划和盈亏。
- 历史复盘视图。

验收：

- 人工可以按比赛、盘口类型、状态和结果过滤候选。
- 每笔交易可追溯到原始候选和判断理由。
- 只提醒和人工确认模式有清晰操作入口。

## 9. 测试与验证计划

必须覆盖：

- `Totals` 已打穿 Over 的通过与拒绝场景。
- `Moneyline` 末段领先但风险不足、价格不足或状态异常的拒绝场景。
- `Spreads` 安全垫不足时的拒绝场景。
- 状态过期、比分缺失、盘口关闭、流动性不足。
- 执行权限分别为只记录、只提醒、人工确认、自动执行。
- 风控额度耗尽、连续亏损暂停、单场风险限制。
- 买入后价格回归、等待结算、异常退出和恢复。

验证顺序：

1. 用静态样例验证候选和拒绝原因。
2. 用回放数据验证状态变化和价格变化。
3. 用只记录模式观察真实直播市场。
4. 用只提醒模式验证人工判断一致性。
5. 用人工确认模式验证交易闭环。
6. 在风控额度极小的条件下开放自动执行。
