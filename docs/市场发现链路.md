# 市场发现链路说明

本文档说明 market discovery 的运行形态。

## 1. 目标

discovery 链路要满足以下目标：

1. 远端粗筛由策略通过 `TradingWorkflow.discovery_queries()` 提供。
2. 框架统一负责分页、限流、cursor 状态、失败重试和结果合并。
3. 本地 universe 精筛由 `TradingWorkflow.select_market()` 决定。
4. WebSocket 的 `new_market` 热发现和后台分页扫描进入同一套 discovery worker。
5. 交易主链路优先级不变，discovery 不能反向阻塞下单、撤单、成交和风控路径。

## 2. 策略侧职责

策略只表达业务意图，不管理框架运行细节：

- `discovery_queries()` 返回一组 `DiscoveryQuery`，例如标题搜索词、tag slug 或其他 Gamma 查询片段。
- 按真实比赛提高命中率：`discovery_queries_for_live_events(events)` 把直播状态 worker 最近同步到的比赛转换成队名级高意图查询。
- `select_market()` 接收框架标准化后的 `Market`，决定是否进入运行时 universe。
- 策略不得设置或依赖 `limit`、`after_cursor` 这类分页字段；框架会覆盖这些字段。
- 业务关键词、阈值和筛选语义放在策略模块内：`src/polymarket_trader/quant/config.py` 和 `src/polymarket_trader/quant/universe.py`。

`TradingWorkflow.discovery_queries()`（[src/polymarket_trader/quant/workflow.py](../src/polymarket_trader/quant/workflow.py)）把配置里的 `discovery_title_searches` 和可选 `discovery_tag_slugs` 转成 Gamma Events keyset 查询参数。`discovery_queries_for_live_events(events)` 读取当前直播源比赛，用队名、显示名和短名生成今日单场高意图查询，优先发现与真实比赛相关的 Moneyline / Spreads / Totals 市场。直播比赛查询会先按状态排序，再按 Polymarket 单场盘口覆盖度排序；例如 SofaScore 返回大量网球比赛时，ATP/WTA 会排在 ITF 等低覆盖赛事前面，避免有限请求预算被不可交易赛事消耗。

官方 API 文档：

- Gamma API 总览：<https://docs.polymarket.com/api-reference/introduction>
- Events keyset 分页：<https://docs.polymarket.com/api-reference/events/list-events-keyset-pagination>

粗筛建议：

- 可以前移到粗筛：Gamma API 原生支持、语义稳定的条件，例如 `title_search`、`tag_slug`。
- 必须保留在本地精筛或交易判断：依赖热态或账户状态的条件，例如盘口深度、spread、价格阈值、持仓、挂单、预算和风控状态。
- 即使条件前移，`select_market()` 仍然是最终 universe 门禁；远端粗筛只负责减少扫描面，不能替代本地业务判断。

## 3. 框架侧职责

框架只处理通用 discovery 编排：

- 为每个 query 维护独立 cursor。
- 按请求预算推进扫描，避免单次 tick 长时间占用事件循环。
- 全量发现是后台业务能力，不因前台页面展示降频；若需要降载，应通过队列合并、协作式让出事件循环或独立 backpressure 处理，不能静态降低发现 SLA。
- 到达某个 query 末页后标记完成；所有 query 完成后结束当前 round 并开启下一轮。
- 过滤扩展传入的分页参数，确保 `limit` 和 `after_cursor` 始终由框架控制。
- 把 Gamma 返回的 event payload 转成 raw market event，再交给 `MarketDiscoveryWorker`。
- 同步 discovery 状态到 supervisor / metrics，供运行时查询。

实现入口：

- 扫描调度：`src/polymarket_trader/runtime/discovery_runner.py`（`DiscoveryQuery` DTO 也在此）
- 策略主类：`src/polymarket_trader/quant/workflow.py`（`TradingWorkflow.discovery_queries()` / `discovery_queries_for_live_events()` / `select_market()`）
- discovery worker：`src/polymarket_trader/workers/market_discovery_worker.py`
- WS 热发现接线：`src/polymarket_trader/runtime/ws_loops.py`

## 4. 调用链

后台分页扫描：

```text
SportsLiveStateWorker.last_games()
-> TradingWorkflow.discovery_queries_for_live_events(games)
-> TradingWorkflow.discovery_queries()
-> runtime.discovery_runner.run_market_discovery_scan()
-> gamma_client.list_events_keyset_by_params()
-> RawMarketEvent.to_raw_market_events()
-> MarketDiscoveryWorker.ingest_source_page()
-> MarketService
-> TradingWorkflow.select_market()
-> MarketRegistry / downstream events
```

市场发现链路的主产物是内存 `MarketRegistry` 和候选运行时事实。`market_discovered`、`market_updated`、`market_filtered_*` 等扫描事件会通过 `_PERSISTABLE_EVENT_TYPES` 走 outbox→`audit_events`（必要时 `markets` 表），用于满足 CLAUDE.md §10「拒绝原因必须可审计」并喂给 `/analytics/funnel`、`/analytics/rejections`。Worker 侧用 `_seen_*` 缓存做"首次拒绝才落审计"的去重，避免每轮重复发现淹没 audit 表；事件 payload 在 `event_sink._project_payload` 中只保留 `market`/`tracked_market`/`discovery_kind`/`strategy_reason` 等轻量字段，丢掉 `raw_market` 等大块原始数据。全量当前市场列表仍以内存 `MarketRegistry` 和 `/markets` 端点为权威，数据库审计只承接事件日志和成交后订单、成交、持仓与账户交易快照。

WS 热发现：

```text
Market WS new_market
-> MarketDiscoveryWorker.ingest_ws_new_market()
-> MarketService
-> TradingWorkflow.select_market()
-> MarketRegistry / downstream events
```

## 5. 扫描状态

`FullMarketDiscoveryState`（[runtime/discovery_runner.py](../src/polymarket_trader/runtime/discovery_runner.py)）记录运行时扫描状态，主要字段如下，完整以源码为准：

- `query_cursors`
- `completed_query_names`
- `next_query_index`
- `round_id`
- `round_started_at`
- `last_round_completed_at`
- `pages_scanned_in_round`
- `markets_seen_in_round`
- `last_tick_requests`
- `last_tick_markets`
- `last_error`
- `consecutive_failures`

这些字段属于框架运行时状态，不属于策略配置。扩展只能通过 hook 影响 query 内容，不能直接操纵 cursor 或 round。

## 6. 默认行为

当扩展没有实现 `discovery_queries()`，或者返回空集合时，框架使用默认 query：

```python
DiscoveryQuery(name="default", params={})
```

框架会在请求参数中补充：

- `active=True`
- `closed=False`
- 内部页大小限制
- 当前 query 的 `after_cursor`

如果当前策略配置为：

```python
discovery_title_searches = ("nba",)
discovery_tag_slugs = ("sports",)
```

框架最终会请求：

```text
GET https://gamma-api.polymarket.com/events/keyset?active=true&closed=false&title_search=nba&tag_slug=sports&limit=50
```

如果直播源里存在 `Bruins vs Sabres` 这类真实比赛，当前策略还会在静态查询前追加类似：

```text
GET https://gamma-api.polymarket.com/events/keyset?active=true&closed=false&title_search=bruins&tag_slug=sports&limit=50
GET https://gamma-api.polymarket.com/events/keyset?active=true&closed=false&title_search=sabres&tag_slug=sports&limit=50
```

这些查询只提高发现命中率，不直接放行交易。是否进入候选仍由本地 universe、市场家族识别、盘口解析、直播状态匹配和风控共同决定。

## 7. 配置边界

框架 `.env` / `Settings` 只承载运行参数和策略装配参数：

- `WORKFLOW_CONFIG_PATH`（可选 TOML / JSON 文件，覆盖 `TradingWorkflowConfig` 默认值）

策略筛选词、价格阈值、流动性门槛等业务配置不进入框架必填环境变量，统一收口在 `TradingWorkflowConfig`。

## 8. 测试关注点

discovery 相关测试应覆盖：

1. 扩展 query 能影响远端请求参数。
2. 框架会覆盖扩展传入的 `limit` 和 `after_cursor`。
3. 每个 query 独立维护 cursor。
4. 所有 query 到达末页后 round 正确完成。
5. 默认 query 在扩展不提供 query 时仍可运行。
6. `new_market` 消息进入同一套 discovery worker。
7. discovery 失败不会清空已有 registry 热态。
8. 请求预算用尽后下一次 tick 能继续推进。
9. 直播比赛生成的高意图 query 优先于静态 query，且按参数去重。
10. 同队伍不同日期的 market 不会被错误匹配到当天比赛直播状态。

## 9. 不做的事

discovery 链路不做以下事情：

- 在 worker 或 infra 中复制业务 universe 判断。
- 让扩展控制框架分页和 cursor 字段。
- 把 closed / archived 市场作为交易主发现面。
- 保留或新增第二套主 discovery 路径。
- 让后台扫描决定交易热路径是否可以继续运行。
